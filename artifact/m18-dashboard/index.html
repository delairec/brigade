Design notes · Home

1. What it is for

One look tells whether brigade works, whether it waits for the user, and what comes next. Today the page lists seven sections of equal weight and the user must read them all to learn that nothing is wrong.

2. Questions, in order

  • Is it alive? The tick heartbeat, in the rail on every page.
  • Does anything wait for me? One list, sorted by what it stops: a parked wave, a parked task, a milestone to merge, a parked study or order, patterns to decide.
  • What is it doing? Open waves with their tasks by state, live runs.
  • What happened while I was away? The last 24 hours.
  • Is the quota a problem? One tile; a blocked wave shows its resume time.

3. Analysis computed

  • The status sentence: stopped, working or idle, from open waves, halts and live runs.
  • The count and the age of what waits; a stall signal whose task merged since is named stale.
  • The day's failed tick actions against the days before.

4. Highlight

  • Sentence first, four tiles, then the list with one call to action per row. Amber means "your move" and appears nowhere else.
  • An idle page says why nothing runs, instead of showing empty lists.

5. Navigation

  • Wave name → wave. Run → run. Inbox items → inbox. Milestone → its report. Project → awawa tab.

Reads

  • brigade status --json: projects, open waves with halt, inbox, quota, last tick, studies, orders.
  • brigade scheduler status --json: the timer, stale, halted waves, parked tasks.
  • brigade ledger --since 1d --json: the last 24 hours.
  • brigade inbox list --json: patterns and stall signals.

Needs

  • status --json: the tasks by state of each open wave, the live runs, and the milestone pull requests waiting for the user's merge.
  • tick --dry-run --json: the name of each decision. Today the two decisions read {"project": "brigade"}, so "next tick" cannot be told.
  • B178 gives the cause of each task not launched.

Waves

A wave is a batch of ratified tasks brigade delivers unattended, one branch and one pull request per task.

read 20:42:29Z · refreshes every 5 s

How to read this page

The tick composes a wave by itself from the tasks that are ready, runs each task through build, checks and review, and merges it. A wave is open until each of its tasks is merged or parked.

A wave that stops is either blocked, on the quota, and resumes by itself at the time shown, or parked, and waits for you. A task parked in a closed wave is served again by a later wave.

Ledger

The ledger is the journal of everything brigade did. This page turns it into measures: what a run takes, whether the turn caps fit, and what keeps failing.

read 20:42:29Z

How to read this page

Every event, a wave started, a pull request merged, a run finished, is one line appended to the ledger. Nothing is rewritten, so the measures here can always be recomputed.

A turn is one step of an agent. Each role has a turn cap per segment: too low and runs hand over again and again, too high and a lost run burns tokens. Brigade recomputes the cap of a role once it has measured enough segments.

Come here after a few waves, to tune a cap, to compare two periods, or to find an action that fails at every tick.

  • Clean is left out: it deletes entities. Changing a colour and arranging columns are not ported in M18.

The shell

  • RailAlways there: the project, the pages in two groups, the addons, and the heartbeat of the tick. A count in the rail is a count of things open now; amber when they wait for you.

  • Project"All projects" or one. The choice travels in the address, so a page can be bookmarked for a project. It narrows waves, runs, inbox, reports and ledger.

  • AddonsAn addon is a tab served by a process of its own. awawa shows when the project chosen has a corpus, or under "All projects" when any has one.

  • PageTitle and one sentence; the explainer; the status sentence or the tiles; what needs you; the blocks; raw detail folded last.

  • PollingEvery 5 s while the tab is visible, as today, but the page swaps a fragment only when it differs from the one shown, and an opened fold stays open.

  • NarrowUnder 900 px the rail becomes a wrapped bar on top; tables scroll inside their panel.

Rulings needed

Each with its options, the one recommended, and the fact it rests on.

  1. How the page reaches the awawa addon

    A, recommended. Through brigade's own routes: the dashboard hands the request to its child over a pipe and renders the answer. One origin, one port. B. The addon listens on a port of its own and brigade relays. C. The addon listens on its own port and the page frames or links it.

    The dashboard sends Content-Security-Policy: default-src 'self', start_dashboard.py:12: a frame or a fetch to another port is refused. A second listener would need the Host and token guards of the decision on the loopback host again.

  2. Who renders the awawa views

    A, recommended. The addon answers the document brigade corpus --view … --json prints, kept warm; the dashboard renders it in Python. The decision "a view is rendered by the server from the JSON of a command" stands, and the command stays the reference of the tests. B. The addon renders the HTML: the decision is amended. C. The addon relays raw awawa answers and the dashboard computes: the cache sits in the wrong process.

    One request of the present Corpus view of 226 tasks took 3.09 s here; the page polls every 5 s.

  3. Which state of the plugin the web tab keeps

    A, recommended. What fits the address: view, type, field, filters, search; folds open by the plugin's defaults. No "Change Colour", no "Arrange Columns" in M18. B. Also colours, column order and folds, in the browser's storage, by a script no test covers. C. Also those, in a file brigade writes, by new POST routes.

    The plugin keeps them in the project's workspace file, handbook §16; the dashboard holds no state today.

  4. A detail pane for an entity

    A, recommended. A click shows the fields of the entity, what refers to it, and links to awawa-web and the IDE. B. As the plugin: rows only, the click leaves for the editor. C. A page per entity.

    The plugin left the pane out because the editor was a double click away, handbook §18.2. On this machine ide_link is unset: under B a click leads nowhere unless awawa-web runs.

  5. How the report page sorts the narrative

    A, recommended for M18. By the first words of each line, "went well", "went wrong", "next", with one plain list when none is found. B. The REPORT schema gains fields the reporting slot fills. Exact, but it changes the installed registry schema. C. No sort: one list.

    Read on the 29 reports of this machine: 19 carry both "went well" and "went wrong" lines, 25 a "next" line, 25 open on "Verdict:"; the report of M8 carries none and would show as one list. Upgrading an installed schema is B197, a draft of M16.

  6. Who shows what M14 adds

    A, recommended. The M18 views render the M14 fields when the document carries them, each proven on a document that holds them: the arguments, segments, duration and cost of B92, the halt and causes of B178, the state filter of B263. B. Each M14 task gains a line for its view. C. A new M14 task for the views.

    B92, B178 and B263 specify commands and no view; only B229 specifies its chart, "under its table Turn cap by role", a place the new Ledger keeps.

  7. New actions in the dashboard

    A, recommended. None in M18: the six POST routes of today, and the command to copy elsewhere. B. Add buttons to resume a parked study and to prune a dead run.

    The routes are listed in route_action.py and route_change.py; M15 is named "Admin console".
