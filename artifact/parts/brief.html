Appendix

The brief behind this plan

The main session, which conducts the work, handed this plan to Max, the role that reasons deepest. Max is read-only on every repository; it may only write its own working files and publish this Artifact. The work ran in two phases: first questions to the user, then design and writing. This page is the brief Max received, together with the clarifications that came during the work.

Goal

Industrialise the use of AI agents on one machine and across all projects, through a CLI and an environment inspired by a talk on software factories and the trust ladder with agents. The deliverable is a published Artifact holding a detailed, spec-like plan, solid enough to build a proof of concept suited to the user's needs and machine, which AI agents can then implement task by task.

What done looks like

  • A spec of the environment and its CLI.
  • Visual mockups (terminal output, tool screens) and diagrams wherever they help understanding.
  • A task page whose statuses persist and can be changed, so agents and the user can track the POC's implementation.
  • A demo page, if it stays light.
  • awawa considered as a possible building block, not as a given.

Working method

  • Questions first. Before designing anything, read the talk's transcript, survey the existing environment, and return a short list of questions. Each one opens with its context, offers concrete options with a recommendation, and says what each answer changes. The design starts once the answers are in.
  • Context discipline. Keep a hand-off file current at each milestone, with the answers, the decisions, the outline and what remains, so a successor run can take over if the work grows long.
  • No side effects. No repository is modified; only the Artifact is published.

Inputs

  • The talk's transcript. Its themes: the trust ladder; verification as the key to autonomy; determinism versus judgment; agent mistakes turned into system constraints; the codebase as prompt; inner and outer loops; a coordinator agent; buffers; sampling-based review; the "dark factory"; verifiability; skills mined from history.
  • The existing environment, to be surveyed rather than trusted:
    • a rules corpus written with awawa, holding rules, triggers, named roles and procedures;
    • Claude Code roles and hooks;
    • a project run in waves of background agents in git worktrees, one pull request per task;
    • repository guards and a coverage gate;
    • a GitHub bot account;
    • usage reports written after each reviewed pull request.
  • An earlier comparison of awawa with the talk:
    • awawa compiles context and rules, not code;
    • coordination exists through the roles, verification through tests, CI and a verifier role;
    • missing: intake of outer-loop signals, a triage buffer, sampling review, systematic mistake-to-constraint mining, deterministic codemods and a cross-project view.

Clarifications received during the work

Scope

The factory is a new, standalone project that applies machine-wide, across every project. The existing project is only one example of current practice. The Artifact is written in English.

Autonomy

The user states an intent, and from there agents work on their own:

  • they plan a wave on an integration branch, split into tasks;
  • they dispatch the tasks in dependency order;
  • they open pull requests, which a specialised agent verifies and which are merged into the integration branch once compliant.

A reporting agent then delivers:

  • a report;
  • the updated dependency graph;
  • a table of manual tests the user may run.

Changes to the global instructions corpus are allowed, provided the report lists them with their reason. Everything is versioned, so nothing is irreversible. The only human gate is merging the integration branch into the project's main branch.

Storage

Hybrid: an awawa corpus for durable facts, and an append-only JSONL ledger for high-volume events.

Intake

All four sources, phased sensibly in the POC:

  • GitHub review threads and CI failures;
  • scheduled gardening scans;
  • a local notes inbox;
  • corrections mined from agent transcripts.
Execution

Local only: a user systemd timer, unattended runs, and background sessions for long runs.

Budget

The user has a subscription, so no cost cap. The plan handles hitting the rate-limit window by pausing and resuming the wave. Usage statistics come from the CLI, not from AI spend. Expected scale: waves of 10 to 20 pull requests.

Mining

Constraints derived from transcripts are produced and merged like any other wave work, and listed in the report with their reason. Anonymisation of personal data is mandatory.

Review

A verifier agent checks every pull request. The user reviews only at the merge into the main branch, with the report and the manual-test table.

Interface

To arbitrate:

  • either keep the IntelliJ plugin currently in use, whose spec is described in an existing Artifact, with the option to display any local branch or worktree without checking it out;
  • or move to a local web server, which allows richer screens: statistics collected by the CLI, project management, corpus browsing.

The name and the CLI's language are Max's to recommend.

awawa

The user is a consumer, not its author. The plan wraps the binary as it is, and any desired change goes to a separate list of requests, never on the POC's critical path.

First principle

The CLI does everything mechanical; agents only judge. Every step of the wave lifecycle is marked as deterministic (CLI) or judgment (agent). Agents receive pre-computed context from the CLI and hand their verdicts back to it, rather than rediscovering state through git, the GitHub CLI or file reads. The diagrams and mockups show this split, an estimate of the AI work saved is given where possible, and the POC tasks start with the deterministic commands.
