Specification · proposal of 2026-10-04 · for a POC

brigade: a kitchen for AI-agent waves, run from one machine

A CLI, a timer and a local dashboard that turn one request into a wave of tasks, run the tasks as agent runs in worktrees, verify every pull request, merge the compliant ones into an integration branch, and hand the user one report and one merge button. The CLI does everything mechanical; the agents only judge.

1Principles

  1. The CLI does everything mechanical; the agent only judges. Creating branches and worktrees, ordering tasks from the dependency graph, launching and polling runs, reading CI and pull-request state, merging, rebasing, collecting statistics, assembling report skeletons and manual-test tables, detecting and normalising signals: none of this needs a model. An agent receives a pre-computed context from one command and returns a verdict or a text through another; it never rediscovers state through git, gh or file reads. Every step in §5 is tagged CLI or agent.
  2. Verification is the gate, not the review. A pull request enters the integration branch when the pass (§7) approves it: deterministic checks first, one specialised agent's judgment second, continuous integration green throughout. The user reads a report, not twenty diffs.
  3. A repeated mistake becomes a constraint. Signals (review threads, failing checks, transcript corrections, gardening scans) are buffered, grouped into patterns, and turned into rules, guards, lint or scripts through the same wave machinery, listed in the report with their reason.
  4. Everything is versioned, so everything is reversible. Waves live on integration branches, corpora in git, the brigade's own facts in a git repository; the only irreversible act, merging into a project's main branch, stays with the user.
  5. One home per fact. Durable, reviewed facts live in awawa corpora (the project's tasks and decisions, the brigade's registry and patterns); high-volume events live in an append-only ledger; views are rendered, never hand-maintained.
  6. Unattended by default, never assuming. A run with nobody to ask keeps, skips or reports what it cannot clear on evidence (@RULE.unattended_procedure_never_assumes). A stuck wave parks with a question; it does not guess.
  7. Agent-agnostic throughout. Roles, rules and procedures in <rootDir> name no CLI (@RULE.instructions_are_agent_agnostic), and neither does the core of brigade: each agent CLI is an adapter of brigade behind one interface (launch a run as a role, detached; a normalised result; resume; transcripts). Claude Code is the first adapter (@DECISION.BrigadeNamesNoAgentCliEachCliIsAnAdapter).
  8. Shareable from the start. No path and no account in the code, all through configuration; the machine account is optional; Linux with user systemd is the one platform; a user without an instructions corpus gets brigade's default roles. The command line is the contract: the shapes of --json outputs and state files are CONTRACT entities of the repository corpus, every command is tested as a black box, adapters and hooks talk to brigade by subprocess and JSON. Installing on another machine is M7, after the POC (@DECISION.BrigadeIsShareableFromTheStart, @DECISION.TheCommandLineIsTheContract).

2Goal, target rung, non-goals

Goal. The user types what they want. From there, without them: a wave is planned on an integration branch and cut into tasks; the tasks are dispatched to agent runs in dependency order; every pull request is verified by a specialised agent and merged into the integration branch once compliant; the next tasks start as their prerequisites land; a reporting agent writes the report, refreshes the dependency graph and fills a manual-test table. Changes to the global instructions corpus are allowed and listed in the report with their reason. The user intervenes once: merging the integration branch into the project's main branch.

Where this sits on the ladder. The overview tab draws the ladder. Today the machine stands at rung 2 (agents build in worktrees, the user launches waves and reviews every pull request). The POC targets rung 4: unattended waves with automatic merges into integration. Rung 5 (merges into main, a wave started by a signal alone) is designed as a policy switch and shipped off.

Non-goals of the POC. No cloud execution; no cost cap (Max x5 subscription, the quota is the cap, §15 handles the window); no codemod engine (a constraint may be a script, the brigade does not write AST tools itself); no rewrite of awawa, awawa-web or the IntelliJ plugin; no multi-user features; no project that refuses a corpus (one is bootstrapped instead).

3Glossary

<rootDir>
The user's instructions corpus (roles, rules, triggers, procedures), named as its own AGENTS.md names it. The brigade reads it as it is; a user without one runs brigade's default roles.
brigade
The whole system: the brigade CLI, its timer-driven tick, its dashboard, its corpus and its ledger. In a kitchen, the brigade is the team under the chef; here the chef is the user and the cooks are the roles of <rootDir>, or brigade's default roles.
project
A registered repository on this machine, with its main branch, its corpus root, its acceptance commands and its per-worktree setup (a PROJECT entity, §11).
request
What the user wants, in their words, for one project (a REQUEST entity). It becomes one wave.
wave
A set of tasks delivered on one integration branch (integration/<slug>), closed by one merge into main. The WAVE and TASK entities live in the project's own corpus, as today.
run
One non-interactive agent session carrying out one procedure for one role, launched by the CLI with a brief, measured in the ledger.
the tick
One deterministic pass of brigade tick: reconcile every active wave with git and GitHub, advance states, launch what is startable, record events. The kitchen's expediter.
the pass
Verification of one pull request: brigade verify's deterministic preflight, then prudence's judgment, then the verdict posted as a review.
signal
One observed fact worth a look: an unresolved review thread, a failing check, a note, a correction in a transcript, a non-zero gardening scan. Normalised by the CLI into the inbox (ledger).
pattern
Several signals that are one thing (a PATTERN entity with its evidence), proposed by the triage run, ratified or dismissed by the user.
constraint
What a ratified pattern becomes: a rule in <rootDir>, a guard, a lint, a schema change, a skill or a script in a project (a CONSTRAINT entity), delivered by a wave.
routine
A scheduled deterministic scan whose non-zero output is a signal (a ROUTINE entity).
ledger
Append-only JSONL events under $XDG_STATE_HOME/brigade/ledger/: runs, steps, durations, states, pauses, merges. Every statistic is derived from it.

4Architecture

Three layers, one principle. The brigade layer is deterministic Python: it knows git, GitHub, systemd and the awawa binary, and reaches each agent CLI through one adapter. The judgment layer is the roles of <rootDir>, launched as runs with a pre-computed context. The record layer is corpora and the ledger.

Task states

Hand-over and budgets inside a run

A run keeps the rules it has today: a step budget from its procedure (@RULE.procedure_step_budget, p90 of past runs), a hand-over at fifty steps to a progress file (@RULE.long_run_hands_over). The CLI makes both mechanical: brigade run passes --max-turns from the budget, reads the hand-over file when the run ends unfinished, and relaunches a fresh run with that file as its first context, up to POLICY.HANDOVERS (2). The ledger records each segment so the p90 is measured on real steps, not on log entries.

6Commands for agents: context in, verdict out

Each judgment run gets two kinds of commands: one that prints everything it needs to start, and one that takes its output and does the mechanical rest. Outputs are bounded (summary on stdout, details in a file under the run's directory), so a run never spends steps re-reading an output too large to display (measured: 146 such steps over 67 launches).

7The pass: verification

A pull request is checked at the pass before it reaches the integration branch. The first half costs no AI step and refuses most defects by itself; the second half is one run of prudence, who holds no memory of the work (@RULE.work_handed_to_role_of_its_nature: delivered work is never verified by the run that produced it).

CLI preflight

  • the branch descends from the integration head (else: rebase path);
  • every check run is green (gh pr checks), including the coverage gate and the browser suites left to CI;
  • awawa fmt --check and awawa lint --strict on the branch, read through the refs cache without a checkout;
  • the promotion is present: task STATUS implemented, DELIVERED_BY = this PR, every SPEC has an IMPL that resolves;
  • no reformat of corpus files the task does not touch (git diff --stat on *.awawa);
  • privacy scan of the diff: 76561198\d{9}, the run-time set of player names from the private saves, e-mail addresses, paths under .do-not-commit;
  • the PR body describes the head (title from the task, acceptance verdicts filled by task pr);
  • size signals for the report: files, lines, packages and layers touched.

agent prudence

  • each SPEC line is proven by the test or code its IMPL names, and nothing else was promoted;
  • tests follow the rules of the triggers the diff touches (TDD, test quality, layer rules);
  • a ruling taken on the way is recorded as a DECISION with its rejections;
  • the change contradicts no recorded decision;
  • findings graded as the review rules say (critical, high, medium, low); only violations, never differences from an example.

Verdict handling

  • approve + green → merge into integration (the merge method is the one @RULE.squash_merge_rebase_update of the instructions corpus names, @DECISION.TheMergeMethodIsTheInstructionsCorpusRuleNotAProjectField), task merged, dependents start;
  • request changes → remi round, then back to the pass; after POLICY.VERIFY_ROUNDS rounds the task is parked with the findings in the report;
  • a critical finding on a core-* package parks at once.

Sampling stays a suggestion: the report lists the three PRs the user might read (largest diff, most rounds, deepest layer touched). Nothing blocks on it.

10The miner

The transcripts on the machine (420 sessions, 735 MB for planet-crafter alone; about 60 more on <rootDir> and the awawa tooling) are the process as it really happened. The miner reads them since a watermark, finds the moments where the user corrected an agent or an agent lost steps, and feeds the inbox. The user's answer: constraints that come out of it are delivered "like a wave", auto-merged into integration, listed in the report with their reason.

CLI extraction

  • reader: the adapter's transcript reader, the one file that knows a CLI's session format (the first adapter reuses the steps reader of <rootDir>'s own adapter); steps counted as distinct answers;
  • heuristics: a user message following an assistant answer with a correction marker (non, pas ça, jamais, ne … plus, wrong, don't, stop); a tool refusal by a hook; the same command repeated more than three times in a run; an output too large to display followed by a read of its file; a review thread that led to a changes-requested verdict;
  • scrubber, mandatory before anything leaves the state directory: 76561198\d{9} → 765611900000000xx; the set of player names computed at run time from the private saves present on the machine and never stored; e-mail addresses; paths under .do-not-commit; a unit test proves that a fixture holding each kind of identifier comes out clean;
  • each finding is a signal with session id and line, so an agent can quote the exact words later.

agent mina, then a wave

  • mina groups the findings into patterns and proposes a constraint: a RULE with an ENFORCED_BY hook when a hook can enforce it; a guard with its test; a lint; a schema change; a script replacing a repeated judgment;
  • the user ratifies; the constraint becomes a request on its target (<rootDir> or the project) and goes through §5: lex writes rules, bastien writes guards, prudence verifies, the report lists each with its reason;
  • the measure of success is the next miner run finding fewer of the same corrections.

11Registry, policies, routines: the brigade corpus

The brigade's durable facts are an awawa corpus in $XDG_CONFIG_HOME/brigade, with its own schema shipped by the tool and installed by brigade init; the directory is a git repository, so every ratification is a commit and awawa-web edits it as structure. Waves and tasks are not here: they belong to each project's corpus, where they already live.

SCHEMA SETTINGS                        // one entity, written by brigade init
	FIELD ROLES imported|default REQUIRED  // the roles of INSTRUCTIONS, or the default roles brigade ships
	FIELD INSTRUCTIONS string             // path of the instructions corpus, when ROLES is imported
	FIELD ACCOUNT string                  // the gh account commands run as; the active login when absent
	FIELD BOT string                      // the machine account that merges and comments; optional

SCHEMA PROJECT
	NAME slug
	FIELD PATH string REQUIRED            // absolute path of the main checkout
	FIELD REMOTE string                   // owner/name on GitHub
	FIELD MAIN string REQUIRED            // master, main
	FIELD CORPUS string                   // workspace root the anchors resolve from; "." for the repository root
	FIELD ACCEPTANCE string REPEATABLE    // light commands run by `task check`: bun test, bun run lint:types, bun run guards
	FIELD HEAVY string REPEATABLE         // suites left to CI, read on the PR: bun run test:ui, audit:quality
	FIELD SETUP string REPEATABLE         // per-worktree commands: bun install --frozen-lockfile, ln -sfn …/input input
	FIELD SLOTS uint DEFAULT 4
	FIELD ADAPTER string                  // the agent-CLI adapter that launches the runs; the first adapter when absent
	FIELD GRAPH string                    // command that regenerates the dependency graph document, if any
	FIELD STATUS active|paused

SCHEMA POLICY
	FIELD PROJECT @PROJECT REQUIRED
	FIELD PLAN_REVIEW ask|auto DEFAULT ask // ask for the first waves of a newly registered project, then auto
	FIELD VERIFY_ROUNDS uint DEFAULT 2
	FIELD HANDOVERS uint DEFAULT 2
	FIELD AUTO_MERGE integration|none DEFAULT integration
	FIELD AUTO_RATIFY uint DEFAULT 0      // occurrences before a pattern ratifies itself; 0 = never (POC)
	FIELD SAMPLING suggestions|none DEFAULT suggestions

SCHEMA ROUTINE
	FIELD KIND gardening|intake REQUIRED
	FIELD COMMAND string REQUIRED         // expected to print nothing and exit 0
	FIELD EVERY string REQUIRED           // systemd calendar expression: daily, Mon 09:00, *:0/30
	FIELD PROJECT @PROJECT                // absent = every active project
	FIELD STATUS active|paused

SCHEMA REQUEST
	FIELD PROJECT @PROJECT REQUIRED
	FIELD TEXT string REQUIRED            // the user's words, verbatim
	FIELD STATUS planning|planned|running|paused|reporting|delivered|closed|cancelled
	FIELD WAVE string                     // the wave number in the project corpus, once planned
	FIELD BRANCH string                   // integration/<slug>
	FIELD FROM @PATTERN                   // when a ratified pattern started it

SCHEMA PATTERN
	FIELD TITLE string REQUIRED
	FIELD STATUS new|ratified|dismissed|delivered
	FIELD EVIDENCE string REPEATABLE      // "pr 287 thread 41", "session 3ea4… line 1180"
	FIELD ACTION wave|constraint|dismiss
	FIELD TARGET string                   // project slug or "instructions" (<rootDir>)

SCHEMA CONSTRAINT
	FIELD TITLE string REQUIRED
	FIELD KIND rule|guard|lint|schema|skill|script REQUIRED
	FIELD FROM @PATTERN REQUIRED
	FIELD TARGET string REQUIRED
	FIELD STATUS proposed|delivered|rejected
	FIELD DELIVERED_BY string             // request id

13Dashboard, IDE plugin, awawa-web

Arbitration. Build the brigade dashboard as a local web page served by brigade serve on 127.0.0.1; keep the IntelliJ plugin unchanged; keep awawa-web as the editor of the brigade corpus. Reasons, each a fact of the current tools:

  • the plugin (awawa-ui 0.8.0, from its handbook) reads one project's checkout through seven awawa --json calls, holds no parser, no server and no other branch; its own gap note names user-defined views (roadmap, burn-up, derived items) as the extension point. The brigade's views are exactly that kind: cross-project, fed by the ledger, with actions (ratify, pause, resume). A plugin would have to grow a server and a ledger reader of its own;
  • a web page served from the machine already exists as a precedent (the user's local context page: a Python stdlib server, one template, polling every 5 s, writes through the server), so the cost is known;
  • the branch selector the user wants is a server-side fact: git archive <sha> into a cache keyed by SHA, then awawa … --json on that tree, no checkout, no worktree opened; a worktree's working tree is read in place so uncommitted edits are visible too;
  • awawa-web already edits a corpus block by block with fmt and lint after each write and a 409 on stale edits: the brigade corpus needs no second editor;
  • both are kept: the dashboard exposes /api/corpus?project=&ref= and the plugin may call it later to gain the selector in the IDE (follow-up B32, outside the POC); nothing is duplicated because the plugin would be a thin client of the same local API.

15Execution on this machine

  • Timer. brigade.timer (user unit, OnCalendar=*:0/5, Persistent=true) starts brigade.service = brigade tick --once. The laptop being off loses nothing: the next tick after boot resumes. Routines carry their own calendar expression and are run by the tick when due.
  • Runs. A run is systemd-run --user --unit brigade-run-<id> … <the adapter's launch command>, in the task's worktree: the adapter starts its CLI headless as the role, with the brief, the capabilities and the budget, its log written under runs/<id>/; the tick reads the adapter's normalised result. journalctl --user -u brigade-run-<id> is the log; the adapter's resume of the session the way back into it. Claude Code is the first adapter (B42, B06); the attachable background sessions of one CLI were rejected as a feature of one adapter, not of the core (@DECISION.BrigadeNamesNoAgentCliEachCliIsAnAdapter).
  • Context injection. The hooks of <rootDir>'s adapter inject a role's package only for sub-agents; a top-level run started by a CLI gets none, so brigade run passes the package itself through the adapter, which hands it to its CLI as part of the system prompt, built once per tick by awawa context @AGENT.<role> --depth 2 --skip reasoning <rootDir>. No run depends on its own diligence to load its rules.
  • Slots and locks. Four runs at once per project by default; one tick at a time (a lock file with the PID); a wave reconciled by one tick at a time.
  • Quota. A result whose error names the rate limit pauses the wave: runs in flight are left to finish or fail, the wave records resume_at from the hour the message names (else now + 30 min), and the first tick after that time resumes each suspended run through the adapter's resume of its session and the prompt "continue from your progress file". The pause itself is the probe; no extra call is spent.
  • Accounts. gh runs as the machine account when SETTINGS.BOT names one (what the shell wrappers do today, reproduced by the CLI reading the keyring with gh auth token --user), else as the user's account; commits carry the attribution lines the session passes.

16Safety envelope

Human-only

  • merging an integration branch into a project's main branch;
  • deleting a branch of main, force-pushing anywhere but a task branch with lease;
  • ratifying a pattern (until AUTO_RATIFY is set);
  • launching max: a wave that needs an arbitration parks with the question and the verified alternative;
  • changing the harness settings file, credentials, the brigade's policies.

Mechanical guarantees

  • with a machine account, branch protection on main: the bot can merge into integration/* only;
  • each run in its own worktree, tools from the procedure's capabilities, the adapter never bypasses its CLI's permission system;
  • every write to a corpus goes through fmt + lint --strict + a commit on a branch;
  • the privacy scan refuses a PR carrying a real identifier before any agent sees the diff;
  • an unattended run never confirms by absence of an answer; a cleanup keeps what it cannot clear;
  • everything is on a branch: a wrong wave is a branch deleted, a wrong rule a revert on <rootDir>.

19Decisions closed since the proposal

The five choices the proposal of 2026-10-04 left open were ruled on 2026-10-05; each ruling is a DECISION of the repository corpus.

  • Long runs: systemd-run with the adapter's headless mode; the attachable background sessions of one CLI are a feature of one adapter and leave the plan (@DECISION.BrigadeNamesNoAgentCliEachCliIsAnAdapter).
  • Merge method: a general rule of the instructions corpus, cited, never restated; PROJECT.MERGE is removed (@DECISION.TheMergeMethodIsTheInstructionsCorpusRuleNotAProjectField).
  • PLAN_REVIEW: ask for the first waves of a newly registered project, then auto; the schema default is ask (@DECISION.PlanReviewAsksForTheFirstWavesOfANewProject).
  • The integration → main PR is opened as late as possible, with the report; earlier when a need requires it (@DECISION.TheIntegrationPullRequestOpensAsLateAsPossible).
  • Dogfooding: M0 and M1 are delivered by the existing machinery, one PR per task; from M2 brigade delivers its own waves (@DECISION.BrigadeDeliversItsOwnWavesFromM2).

Ruled the same day, outside the five: brigade is shareable from the start, with the installation on another machine as M7 (@DECISION.BrigadeIsShareableFromTheStart); the command line is the contract (@DECISION.TheCommandLineIsTheContract); Rust was weighed and the Python ruling stands (@DECISION.PythonStandardLibraryOnly).
